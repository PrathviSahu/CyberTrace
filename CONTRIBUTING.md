# Contributing to CyberTrace

Thank you for contributing to **CyberTrace**! This project is an AI-native Security Operations Platform built for defensive cybersecurity operations.

---

## 1. Defensive Security & Ethical Standards

- **Strictly Defensive Mission**: CyberTrace is designed exclusively for threat detection, incident investigation, and defensive response coordination.
- **Synthetic Data First**: Never commit real production credentials, real personal identifiable information (PII), or live internal enterprise network dumps. Use synthetic datasets generated by `backend/app/data/synthetic_generator.py`.
- **Zero Secret Exposure**: Never commit `.env` files or API keys. Always use `.env.example` as a template with empty strings for secrets.

---

## 2. Core Architectural Principles

When writing or reviewing code for CyberTrace, adhere to these three non-negotiable rules:

1. **Deterministic Authority**:
   Detection rules and incident correlation algorithms are authoritative. AI models (`qwen-3.8-27b`) perform investigation, synthesis, and hypothesis generation—they never override or hallucinate raw detection verdicts.
2. **Strict Evidence Grounding**:
   Every observed fact and recommended action produced by AI must cite valid, verified event IDs (`[evt_...]`) present in the incident evidence dossier. Unsupported claims must be stripped by `EvidenceVerifier`.
3. **Operational Transparency**:
   All metrics, charts, and incidents must carry an honest `DataProvenanceBadge` (`Live Telemetry`, `Demo Benchmark`, or `Calculated Evaluation`). Never present synthetic mock fixtures or failed requests as successful live calculations.

---

## 3. Development & Branching Workflow

```
main (Protected baseline)
  └── feature/phase-4-soc-frontend (Active integration branch)
        ├── feat/your-feature
        └── fix/your-bugfix
```

1. **Branch Naming**:
   - `feat/description` for new features or endpoints.
   - `fix/description` for bug fixes.
   - `docs/description` for architectural or guide documentation.
2. **Local Pre-Flight Verification**:
   Before creating a Pull Request, you MUST run:
   ```bash
   # 1. Backend tests
   source backend/.venv/bin/activate
   PYTHONPATH=backend pytest backend/tests -v

   # 2. Frontend typecheck & build
   cd frontend
   npm run build

   # 3. Git diff whitespace check
   git diff --check
   ```
3. **Atomic Commits**:
   Write conventional commit messages: `feat:`, `fix:`, `docs:`, `test:`, `refactor:`.

---

## 4. Pull Request Checklist

When opening a Pull Request, ensure:
- [ ] All new backend code has corresponding pytest unit or integration tests.
- [ ] No regression in the existing 74 backend tests.
- [ ] Frontend builds with 0 TypeScript errors and 0 warnings.
- [ ] No `.env`, database (`.db`), or temporary files are staged.
- [ ] The PR description clearly explains the changes and references any open issues.
